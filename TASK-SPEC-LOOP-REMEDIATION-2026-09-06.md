## 1. ПОДТВЕРЖДЁННЫЕ дефекты (воспроизведены живьём)

### D1 — ложный PASS: отсутствие обеих копий приказа не является нарушением (закрывает L5)

Проба в памяти, рабочие файлы не подменялись, файлы команд поданы **настоящие**; единственная
переменная — отсутствие `CLAUDE.md`. Оба случая (нет обеих копий; нет репозиторной) дают
`rc=0 PASS copies=2 section_match=true violations=0` — см. N1/N2 в §1b. Причина в коде,
`scripts/spec-loop-install-check.py`, ветка `if text is None`:

```python
if text is None:
    print(f"  {name}: ABSENT (операторский дом вне сборки — не нарушение)")
    continue
```

Послабление введено ради CI, где операторского дома нет, но применяется и к **репозиторному**
`CLAUDE.md`, который в сборке присутствует всегда. Проверка, подтверждающая отсутствующую
установку, установку не проверяет.

**Что сделать:** развести два класса целей — отсутствие глобального `~/.claude/CLAUDE.md`
допустимо только при `CI=true`, отсутствие репозиторного всегда FAIL; случаи N1–N4 §1b
внести в `--self-test`.

### D2 — `copies=N` считает проверяемые записи, а не найденные копии

В пробах выше `copies=2` напечатано при **нуле** фактических копий: показатель охвата, не
зависящий от результата, охват не измеряет. **Что сделать:** печатать
`copies=<найдено>/<ожидалось>`; найдено < ожидалось — FAIL, с оговоркой по глобальному файлу из D1.

### D3 — обязательная вычитка канона не охватывает петлю (закрывает L3)


Маршрут вычитки печатает CORE-10, оргиерархию, замок, роль, гейты `canon-ssot-check.sh` и

Дополнительно: `.claude/rules/gsd-methodology.md` по-прежнему называет спецификацией запись

### D4 — самотест печатает зашитую константу и сеет ложный FAIL в журнал CI

Строка `checks=13` — литерал в коде, фактических вызовов проверки десять плюс отдельная
проверка идемпотентности.

**Находка, которой в вердикте нет.** Прогон `--self-test` печатает в общий поток:

```
spec-loop: FAIL
GATE_RESULT name=spec-loop mode=CHECK status=FAIL commands=8 copies=2 section_match=false
spec-loop self-test: PASS проверок 13, нарушений 0
GATE_RESULT name=spec-loop mode=SELF_TEST status=PASS checks=13 violations=0
```

Первые две строки — ожидаемая отрицательная проба внутри самотеста. Но по форме они
неотличимы от настоящего провала гейта: любой сборщик, снимающий строки `GATE_RESULT`
или ищущий `status=FAIL`, получит из УСПЕШНОГО самотеста запись о провале.

**Что сделать:** считать число проверок фактически, а не константой; отрицательные пробы
внутри самотеста печатать под отдельной меткой (например `PROBE_RESULT`), никогда не
`GATE_RESULT`.

### D5 — ожидание без предела запирает исполнительный слот (найдено живьём, класс L10)

Замер CENTRAL 2026-09-06 ~13:56Z. Окно исполнителя выполняло в одном вызове:

статусом `queue-operation/enqueue` (13:39:38 и 13:41:35) и прочитаны не были. Внешне это
неотличимо от зависания.

|---|---|---|

требования L10 «у ожидания обязаны быть измеренное основание и предел».

## 1a. L10 — НЕПРЕРЫВНОСТЬ ИСПОЛНЕНИЯ (обязательное требование, не пояснение)

Дефект, ради которого пункт заведён: техническая часть петли установлена, а условие
непрерывности осталось словом в тексте. Условие, не вынесенное в требования, порядок работ и
критерии приёмки, не проверяется — и потому не действует. Предыдущая редакция этого задания
сама воспроизвела дефект, завершившись фразой, создающей контрольную точку.

**Норма.** Подготовка файла, передача задания, коммит, запуск CI, завершение отдельной стадии
и отчёт о ходе работ **основаниями остановки не являются**. После `NOT CLEAN` исполнитель
немедленно закрывает поимённо названные незакрытые пункты и выполняет повторный review — без
нового разрешения между стадиями. Краткие сообщения о ходе работы допускаются и работу не
прерывают.

**Ожидание.** Техническое ожидание сопровождается наблюдением за предметом, а не полем
статуса: длительность против собственной нормы предмета, рост вывода, состав исполнителей,
изменение с прошлой проверки. У ожидания обязаны быть измеренное основание и предел;
превышение нормы немедленно превращает ожидание в расследование. Формула «ждём» контролем
не является.

**Единственное исключение — настоящая развилка:** необратимое состояние, изменение нормы,
распределение подотчётности, полномочия, юридический режим, безопасность. Тогда исполнитель
сам пишет бриф в дерево (факты с указанием способа замера, неразрешённое решение, варианты с
ценой каждого, последствия, заблокированные ID требований), называет путь к нему и
останавливается. Консультантам бриф не отправляется: его размещает оператор.

**Согласование со всеми носителями петли.** Формулировка L10 обязана присутствовать
непротиворечиво во всех действующих инструкциях, через которые петля исполняется:

| Носитель | Что проверить |
|---|---|
| `~/.claude/CLAUDE.md`, раздел `SPEC-LOOP-SECTION` | нет остановок между `/spec`, `/build`, `/review` |
| `wt/crypto01/CLAUDE.md`, тот же раздел | побайтово совпадает с глобальной копией |
| `governance/spec-loop-template.md` | то же требование в самом шаблоне |
| четыре файла команд на обоих уровнях | ни один не предписывает ждать вызова следующей команды |
| `.claude/rules/gsd-methodology.md` | закрытие задачи не сводится к переводу IL в DONE |

Расхождение между носителями — дефект: два файла с разными редакциями приказа означают, что
действует тот, который прочитан последним, а это случайность, а не норма.

**Базовый замер носителей, снятый CENTRAL 2026-09-06 ~15:42 CEST — уже сделанное не переделывать:**

| Носитель | Замер | Вывод |
|---|---|---|
| `~/.claude/CLAUDE.md` ↔ `wt/crypto01/CLAUDE.md` | обе копии раздела `sha256=7711b104d7b0af7e`, 8192 байт | **совпадают побайтово — расхождения нет** |
| четыре команды × два уровня (8 файлов) | стоп-фраз: 0 в каждом | **остановок между стадиями не предписывают** |
| `governance/spec-loop-template.md` | «NOT CLEAN → немедленный FIX → снова REVIEW, между итерациями разрешений не запрашивается»; таблица команд: BUILD→REVIEW→интеграционный цикл | **условие непрерывности в тексте есть** |
| единственное совпадение по стоп-фразам | объяснительная преамбула редакции 2 («первая редакция предписывала ждать вызова следующей команды») и норма развилки | **ложные срабатывания, не дефект** |
| `.claude/rules/gsd-methodology.md` | упоминаний петли: 0 | **дефект: не охвачен** |

Отсюда: текстовая часть L10 в трёх носителях **уже выполнена**. Незакрытыми остаются ровно два
предмета — охват GSD-методологии и **машинная проверяемость**: гейт не умеет отвергнуть
носитель, в который остановка вернулась, поэтому сегодняшнее совпадение держится на
добросовестности, а не на проверке. Условие, соблюдение которого нечем опровергнуть, нормой
не является.

**Как L10 проверяется.** Не декларацией, а фактическим прохождением: дефект → исправление →
повторная проверка, без разрешения между стадиями; машинная часть — случай N7 §1b.

   1–8 не завершается ожиданием ответа оператора. Носители петли из таблицы §1a приводятся к
   одной редакции; проверка установки учится отвергать вернувшуюся остановку.

## 5. Определение готовности задания

- Отрицательные пробы A и B дают FAIL и зафиксированы в самотесте.
- `canon-read.sh` печатает статус петли; расхождение GSD ↔ `specs/` снято.
- Самотест не печатает `GATE_RESULT ... status=FAIL` при успешном прогоне.
- Определение CLEAN не содержит merge.
- По каждому ID L1–L9 предъявлен review со статусом и доказательством.
- Все носители петли из таблицы §1a несут одну редакцию условия непрерывности; расхождений нет.
- L10 подтверждён **фактическим прохождением**, а не декларацией: в журнале предъявлена цепочка
  «дефект → исправление → повторный review» без разрешения оператора между стадиями.
- Проверка установки отвергает носитель, в который вернулась остановка между стадиями (случай N7),
  и не даёт ложных срабатываний на преамбуле редакции 2 и норме развилки.
- Все восемь отрицательных случаев N1–N8 из §1b прогоняются самотестом с ожидаемым результатом.
- D5 закрыт: ожидание CI имеет предел, привязанный к норме, выходит с диагностикой и не
  запирает окно исполнителя — проверено фактом приёма задания во время ожидания.
- Интеграция последующих исправлений проверена по свежим SHA; main после merge зелёный.
