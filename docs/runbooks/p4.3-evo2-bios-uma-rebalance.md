# Runbook: P4.3-evo2 — BIOS UMA rebalance (64/64 → 32/96)

**Sprint anchor:** ADR-018 §"Required sprints to reach 100%" item 1.
**Goal:** unblock `qwen3:235b-a22b` (134 GiB) on evo2 by giving CPU side ≥96 GiB RAM.
**Risk:** medium — physical reboot + BIOS edit; evo1 stays online (LiteLLM LB falls back to evo1-only routes during the window).
**Estimated downtime (evo2):** 15-20 min wall-clock.
**Pre-flight discovery:** /tmp/p4-config-discovery.txt (snapshot 2026-05-04).

---

Snapshot current evo2 state for after/before diff:

## 1. Pre-reboot graceful stop (operator on Legion shell)

Order matters: stop dependents first (RPC worker → ollama → docker observability stack). systemd will not restart these on reboot if explicitly stopped, but the units are `enabled` so they come back automatically — that's intentional.

```bash
# 1.1 — drain LiteLLM v2 evo2 routes (route only to evo1 during window)
#       (LiteLLM has retry+fallback; explicit drain is OPTIONAL — skip if you trust LB)

# 1.2 — stop llama-rpc-worker so glm-master on evo1 stops issuing RPC calls into a dying node
ssh evo2 'sudo systemctl stop llama-rpc-worker.service'
ssh evo2 'systemctl is-active llama-rpc-worker.service'   # → inactive

# 1.3 — stop ollama (waits for in-flight requests up to default timeout)
ssh evo2 'sudo systemctl stop ollama.service'
ssh evo2 'systemctl is-active ollama.service'             # → inactive

# 1.4 — stop monitoring containers (prometheus on evo2 will lose 15-min scrape window — acceptable)
ssh evo2 'docker stop banxe-grafana banxe-blackbox'

# 1.5 — sync filesystem buffers
ssh evo2 'sync && sleep 2 && sync'
```

Verify nothing critical pending:

```bash
ssh evo2 'ss -tn state established | grep -vE "ssh|::1|127\.0\.0\.1" | head'
# Expect: empty or only ssh management connections.
```

## 2. Reboot (operator physically at evo2)

```bash
ssh evo2 'sudo reboot'
```

**At the GMKtec EVO-X2 machine:** spam **Del** (or **F2** — depends on BIOS revision; both work on Strix Halo) immediately as POST starts. If you miss the window, system will boot Linux normally — `ssh evo2 'sudo reboot'` again.

---

## 3. BIOS path (manual — at evo2 console)

Exact menu path for AMD AGESA on GMKtec EVO-X2 firmware:

```
Advanced
  └─ AMD CBS
      └─ NBIO Common Options
          └─ GFX Configuration
              └─ UMA Frame Buffer Size
                  → change from [Auto] / [64G] to [32G]
              └─ iGPU Configuration → keep [UMA_SPECIFIED]
```

Then:

```
Save & Exit → Save Changes and Reset
```

If `UMA Frame Buffer Size` option is missing or greyed-out:
- Check that **Above 4G Decoding** is **Enabled** in Advanced → PCI Subsystem Settings.
- Check **Resizable BAR** is **Enabled**.
- Check `iGPU Configuration` is `UMA_SPECIFIED` (not `Auto` — Auto hides the size selector on some AGESA revs).

## 4. Post-reboot verification (operator on Legion shell)

Wait ~60s after boot completes before SSH (network bring-up). Then:

```bash
ssh evo2 'free -h | head -3; cat /sys/class/drm/card0/device/mem_info_vram_total' \
  > /tmp/evo2-post-reboot.txt
cat /tmp/evo2-post-reboot.txt
```

**Expected (PASS criteria):**
- `MemTotal` (free -h "Mem:" total): **≥ 94 GiB** (was 62 GiB; gained 32 GiB to CPU side)
- `mem_info_vram_total`: **34359738368 bytes (32 GiB)** (was 64 GiB)

If MemTotal still shows 62 GiB → BIOS change did NOT persist. Repeat step 3 and explicitly **Save Changes** (not just Exit).

## 6. Smoke test — qwen3:235b-a22b unblocks (operator on Legion shell)

This is the whole point of the rebalance:

```bash
# Should succeed now (134 GiB needs CPU side ≥ 96 GiB; we now have ~94-96 visible).
ssh evo2 'ollama run qwen3:235b-a22b "Reply with exactly: OK." --verbose 2>&1 | tail -8'
```

**Expected:** model loads (may take 60-180s on first run for cold mmap), prints `OK.`, then `eval count`/`eval rate` lines appear.

If you get **"out of memory" / "model requires X memory"** → the rebalance under-shot. Either:
- Reboot again, set UMA to **16 GiB** (gives ~108 GiB CPU side), or
- Use `qwen3:235b-a22b-banxe` if it has a tighter quant.
